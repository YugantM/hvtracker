# Provenance Landscape — Research Summary

**Date:** 2026-05-24
**Purpose:** Inventory of cryptographic and supply-chain trust signals that are (a) publicly queryable, (b) unilaterally observable (no maintainer opt-in for HVTracker), (c) per-AI-agent-project aggregable, and (d) achievable at zero compute budget. Input for owner decision on which signal to implement first.

**Scoring legend (used in each section):**
- **Queryability:** Free / Free w/ token / Rate-limited / Requires scraping
- **Effort:** S (≤1 day) / M (2–4 days) / L (>1 week)
- **Strategic value:** ★ ★★ ★★★ — how distinctive the signal is as a trust differentiator that nobody else has aggregated per agent

---

## 1. Sigstore (cosign / rekor / fulcio)

**What it is.** Sigstore is the OpenSSF-stewarded keyless signing stack. `cosign` produces signatures for container images and arbitrary blobs; `fulcio` issues short-lived signing certificates tied to OIDC identity (e.g. a GitHub Actions workflow); `rekor` is a public append-only transparency log of every signing event. Any party can prove "this artifact was signed by this identity at this time" without trusting a private key.

**Queryable?** Yes — Rekor's public instance (`rekor.sigstore.dev`) is a free REST API. **However, Rekor v1 is being retired in 2026**; the v2 endpoint (`/api/v2/log/entries`) intentionally **dropped** the `Get-By-Log-Index` and `Get-By-Leaf-Hash` lookups and only exposes a single write/read endpoint. **Practical implication:** discovering all signing events for "project X" against bare Rekor v2 is hard; you need an indexer. Existing indexers: `rekor-monitor` (OpenSSF) and `search.sigstore.dev` (now deprecated mid-transition).

**How HVTracker aggregates per agent.** For each agent's GitHub repo and release artifacts:
1. Hash the latest published artifact (release tarball / container image digest from GHCR).
2. Query rekor by artifact digest → list of attestations.
3. Cross-reference the signing identity in the Fulcio cert against the repo's GitHub Actions workflow URL.
4. Surface as boolean (`signed: yes/no`) + count of signed releases.

**Effort.** **M.** Rekor v2 transition adds friction. Best near-term route: detect signing **via npm/PyPI attestation metadata** (sections 3–4) which embed Rekor log entries, rather than querying rekor directly.

**Strategic value.** ★★★ — the canonical cryptographic signal for "this release came from this pipeline." Worth surfacing, but better fetched transitively (via the package registry's provenance field) than directly.

## 2. SLSA framework

**What it is.** Supply-chain Levels for Software Artifacts. A spec, not a tool. The **Build track** has levels:
- **L0** — no provenance
- **L1** — provenance exists (any format)
- **L2** — provenance signed, hosted on the build platform
- **L3** — provenance generated by an isolated, hardened builder (e.g. GitHub Actions reusable workflows with `attest-build-provenance`)

**Queryable?** **No first-class API returns "repo X is SLSA L3."** SLSA level is a derived attribute, computed by inspecting the presence and shape of provenance attestations. Tools that compute it: `slsa-verifier` (CLI, verifies provenance bundles) and **OSSF Scorecard** (has a `Binary-Artifacts` and `SBOM` check, plus an emerging SLSA-readiness signal). GitHub's own changelog (Jan 2026) added native L3 attestation surfacing in the repo UI but no public per-repo "level" API yet.

**How HVTracker aggregates.** Approximate SLSA level via observable inputs:
- Does the repo's latest release have a `.intoto.jsonl` attestation asset? → L1+
- Does that attestation chain to Sigstore + GitHub OIDC? → L2/L3
- Does the workflow use a SLSA-conformant reusable builder (e.g. `slsa-framework/slsa-github-generator`)? → L3 confidence

**Effort.** **M–L.** No turnkey API. Requires custom heuristic per ecosystem (release assets for Python/JS, image manifest for containers).

**Strategic value.** ★★★ — SLSA is the **single most cited framework** in supply-chain conversations. An HVTracker column titled "SLSA build level (observed)" with honest methodology would be genuinely novel; nobody publishes this per AI agent.

## 3. npm provenance

**What it is.** Since 2023, npm publishers can opt into emitting an in-toto SLSA provenance statement at publish time. Stored in the npm registry, signed via Sigstore, logged to Rekor. Verifiable end-to-end with `npm audit signatures`.

**Queryable?** **Yes, trivially.** Two endpoints:
- Package metadata: `GET https://registry.npmjs.org/<pkg>/<version>` → look for `dist.attestations` field. Presence/absence is a direct boolean.
- Full bundle: `GET https://registry.npmjs.org/-/npm/v1/attestations/<pkg>@<version>` → the signed in-toto bundle, including Rekor `logIndex`.

No auth, no rate limits at HVTracker's scale.

**How HVTracker aggregates.** For each agent that publishes to npm (we already have ~20 such packages tracked):
- Fetch `dist.attestations` for the latest version.
- Boolean column: "npm provenance ✓" or "—"
- Optional: count of recent versions with provenance vs without (provenance adoption trend).

**Effort.** **S.** One added HTTP call inside the existing npm fetcher. Maybe 2–3 hours including tests + column.

**Strategic value.** ★★★ — **highest signal-to-effort ratio of any item in this document.** It's the natural first signal: directly observable, well-documented API, plugs into our existing npm path, immediately differentiates agents that ship trustworthy releases from those that don't.

## 4. PyPI trusted publishers + attestations (PEP 740)

**What it is.** Two-layer system:
- **Trusted Publishers (2023):** OIDC-based, replaces long-lived API tokens. Maintainer connects PyPI project to a GitHub Actions workflow; no secrets in CI.
- **PEP 740 attestations (Nov 2024, GA):** When a release is published via Trusted Publisher using `pypa/gh-action-pypi-publish`, an in-toto attestation is automatically generated and stored. As of late 2024, ~20,000 packages emit them by default.

**Queryable?** **Yes, via the PyPI Integrity API.** Endpoint operates per-file (PyPI is file-oriented, not version-oriented). Returns published attestations for a given `.whl` or `.tar.gz`. Trail of Bits maintains a public dashboard ("Are we PEP 740 yet?") tracking adoption among top-360 packages.

**How HVTracker aggregates.** For each PyPI-distributed agent:
- Fetch latest release's file list from `https://pypi.org/pypi/<pkg>/<version>/json`.
- For the wheel, call the Integrity API.
- Boolean column + (bonus) "uses Trusted Publishers" flag (inferable from the attestation's issuer identity).

**Effort.** **S.** Symmetric to npm. ~3–4 hours.

**Strategic value.** ★★★ — same logic as npm provenance. **Shipping #3 + #4 together gives HVTracker a coherent "package-level provenance" cross-ecosystem column on day one.** Strongly recommended as the launch pair.

## 5. Reproducible Builds

**What it is.** A practice (and a movement, `reproducible-builds.org`) where two independent builds of the same source produce bit-identical outputs. The canonical adopter is Debian; mainstream language ecosystems lag badly.

**Queryable?** **Effectively no for AI agents.** Reproducible-builds.org tracks distro packages (Debian, Arch, NixOS, Fedora) — not GitHub/PyPI/npm release artifacts. Verifying reproducibility for an arbitrary AI agent project requires actually re-running the build, which violates our zero-compute constraint.

**How HVTracker aggregates.** Realistically: don't, for now. If we ever wanted to, we could surface "this package exists in nixpkgs and nixpkgs is bit-reproducible at >95%" as a transitive signal, but that's a stretch and few AI agents are packaged for nix.

**Effort.** **L** if attempted properly. Out of scope.

**Strategic value.** ★ — high in principle, near-zero in practice for this ecosystem. **Skip for now.** Note it in the spec as "not currently measurable; deferred."

## 6. in-toto attestations

**What it is.** The underlying **format** used by SLSA provenance, npm provenance, PyPI attestations, and GitHub Artifact Attestations. A standard JSON envelope binding a `subject` (artifact + digest) to a `predicate` (assertion about it — build provenance, SBOM, test results, vulnerability scan, etc.). Specified by the in-toto project (CNCF graduated).

**Queryable?** **Yes, but storage is fragmented.** Three main stores:
- **Sigstore Rekor** — public, default for OSS.
- **GitHub Artifact Attestations** — exposed via `GET /repos/{owner}/{repo}/attestations/{subject_digest}` and `gh attestation verify`. Free, requires a token, generous rate limits.
- **Archivista** (in-toto's own graph store) — GraphQL API, but only contains what people upload to it; sparse for AI agents.

**How HVTracker aggregates.** For each agent's GitHub repo: call the artifact attestations endpoint for the latest release tag's artifacts. Count attestations + classify predicate types (provenance, SBOM, vulnerability, custom).

**Effort.** **M.** Per-repo iteration, multiple artifact digests per release, predicate classification logic.

**Strategic value.** ★★ — overlaps significantly with #1, #2, #3, #4. Best treated as the **underlying format we report on**, not as a standalone column. The spec should reference in-toto as the canonical predicate format.

## 7. GitHub-native signals

The richest, most queryable set of signals — and all already inside our existing GitHub API budget.

| Signal | API | Notes |
|---|---|---|
| **Signed commit ratio** | `GET /repos/{o}/{r}/commits` returns `commit.verification.verified` per commit. | Sample N most recent commits; compute % signed. Cheap. Highly distinctive — many AI agent repos have 0% signed, a few (e.g. anything published from a corp like Microsoft) approach 100%. |
| **Branch protection on default branch** | `GET /repos/{o}/{r}/branches/{branch}/protection` — requires the auth'd user to have admin perms. **Not queryable for repos you don't own.** | Dead end for HVTracker. Skip. |
| **Required signed commits on default branch** | Same endpoint, same limitation. | Skip. |
| **Rulesets (public visibility)** | `GET /repos/{o}/{r}/rulesets` — **public**, no admin perm needed for the listing. | Can detect *whether* rulesets exist and target the default branch, without seeing every rule. Imperfect proxy for "this repo has merge discipline." |
| **CODEOWNERS coverage** | Read `.github/CODEOWNERS` via contents API; compute % of repo paths covered. | Trivial. ~5 min query, modest interpretation logic. |
| **GitHub Artifact Attestations** | Covered in §6. | The "L3 SLSA" indicator in practice. |
| **Release signature/cosign asset** | `GET /repos/{o}/{r}/releases/latest` — check for `.sig`, `.cert`, `.intoto.jsonl` assets. | One call. Direct boolean. |
| **Verified release author** | Releases endpoint includes the publishing user; combine with `verification` field on the underlying tag. | Indicates the release tag itself was signed. |

**Strategic value.** ★★★ for **signed commit ratio**, ★★ for the others, ★ for branch protection (mostly unobservable for third-party repos).

**Effort.** Signed commit ratio: **S** (one new field, sample last 100 commits, store percentage). CODEOWNERS: **S**. Rulesets + release asset signals: **S**.

## 8. Adjacent existing systems (what we can learn from, or use as inputs)

### deps.dev (Google)
- Aggregates package data from Crates, Maven, npm, PyPI, NuGet, Go, etc.
- **Free public API.** Per-project endpoint returns: license, OSV advisories, OSSF Scorecard score (transitively!), default version, dependency graph.
- **Lesson for HVTracker:** deps.dev is the closest existing aggregator. But it is per-**package**, not per-**agent**. It does not editorialize, doesn't curate, doesn't rank. We are not competing — we are downstream consumers + adding the agent-specific narrative layer.
- **Potential use:** call deps.dev API once per agent's primary package to get OSV count, license, and (importantly) **OSSF Scorecard** transitively. **Effort: S.** **This is potentially the single biggest force-multiplier in the entire document** — one API call exposes ~18 sub-signals for free.

### OSSF Scorecard
- Independent project, also queryable via its own `api.securityscorecards.dev` endpoint.
- Returns a score 0–10 plus per-check breakdown: `Binary-Artifacts`, `Branch-Protection`, `CI-Tests`, `CII-Best-Practices`, `Code-Review`, `Dangerous-Workflow`, `Dependency-Update-Tool`, `Fuzzing`, `License`, `Maintained`, `Packaging`, `Pinned-Dependencies`, `SAST`, `Security-Policy`, `Signed-Releases`, `Token-Permissions`, `Vulnerabilities`, `Webhooks`.
- **Already runs daily on every popular GitHub repo.** Coverage of our 65 agents is likely >90%.
- **Lesson:** they have invested years in computing exactly the kind of signals we want. We should consume their score, surface the sub-checks we care about (`Signed-Releases`, `Pinned-Dependencies`, `Branch-Protection`, `Code-Review`) as their own columns, and credit Scorecard. **Don't reinvent.**
- **Effort: S.**
- **Strategic value: ★★★.** Possibly the highest-ROI integration in this whole document, alongside §3/§4.

### Snyk Advisor
- Publishes per-package health scores (free public web pages, but **no documented public API**). Would require scraping. Skip on principle.

### OSV.dev
- Vulnerability database, free API. For each agent's package, returns active CVEs.
- Already partially covered transitively via deps.dev. Direct integration is a few hours if we want freshness.
- **Strategic value: ★★** — useful, but lots of others already surface CVEs. Less distinctive.

## Cross-cutting observations

1. **The single highest-leverage move is consuming OSSF Scorecard via API + deps.dev.** One API call per agent gives us roughly 18 sub-signals computed by a well-funded, well-known third party we can attribute. It bootstraps the entire provenance column to a credible baseline overnight.

2. **The most ownable, distinctive new column is "package provenance" (#3 + #4 combined).** It's directly observable, in our existing fetcher path, and **no leaderboard for AI agents currently surfaces it**.

3. **Signed commit ratio (#7) is a sleeper.** Easy, cheap, almost no AI agent project currently looks good on it — which makes it a strong differentiator for the ones that do, and a credible "room to improve" signal for the ones that don't.

4. **Skip in this phase:** Reproducible Builds (#5, not measurable), direct Rekor queries (#1, transition turbulence), branch protection details (#7, admin-only).

5. **Spec implications.** The Methodology v2.0 spec should define a **Provenance Score** as a weighted composite of:
   - Package-level provenance (npm/PyPI attestations) — heaviest weight (most direct cryptographic guarantee)
   - OSSF Scorecard `Signed-Releases` + `Pinned-Dependencies` + `Branch-Protection` checks
   - Signed commit ratio (sampled)
   - GitHub Artifact Attestations presence on latest release
   - SLSA level (observed, heuristically)
   - Each signal MUST be reported individually (not just the composite), so consumers can audit our methodology.

## Recommendation to owner (deferring to your choice)

**Suggested first signal to ship (Priority 2):** **OSSF Scorecard integration** as the foundation column, **plus npm + PyPI package provenance** as the first HVTracker-original column.

Rationale:
- Scorecard gives us an immediate credible "supply chain hygiene" baseline for ~60/65 agents in one afternoon.
- Package provenance (#3 + #4) is the first column that is *uniquely* HVTracker — nobody surfaces it per AI agent today, and it's the truest cryptographic signal in the document.
- Combined effort: **~1–2 days of focused work**, well within the cadence we've been operating at.
- The combination naturally seeds Spec v2.0 §5 (Provenance Signals) with concrete, defensible, formally-defined content.

**Alternative first signal if you'd prefer a single, fully-owned ship:** signed commit ratio alone. Fast, ownable, no third-party dependency.

**Awaiting your decision on which to implement first before writing any code.**
