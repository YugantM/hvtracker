## Key finding: one dimension dominates

`package_provenance_drift` contributes ±4–5 points and appears as the largest
term in **every** top swing, both directions. The other three runtime
dimensions are small (mcp ≤ +2.0, ext-deps ≥ −3.0, tool-surface ≥ −2.5).
In effect, v2 as currently calibrated is mostly a provenance-drift reweight
with runtime garnish. Before this drives production rank, the drift signal's
false-positive rate needs review — a "mismatch" status is worth −5.0 only if
mismatches are reliably real, not packaging noise.

## Addendum 2026-07-02: same-owner drift fix, re-review

Owner decision on this report: fix the drift detector's false-positive rate
first (option A), then re-run. Investigation of the six A-grade droppers found
the `-5.0` "warning" penalty conflated two different situations: a genuine
different-owner package mismatch (real ambiguity — could be squatting or an
unrelated collision) vs. a **same-owner, different-repo** mismatch (a JS/Python
split, a rename, a monorepo carve-out — not evidence of hijack). Dataset-wide,
**12 of 26 warning-status agents (46%)** were the same-owner pattern.

**Fix shipped:** `detect_package_provenance_drift` now scores a same-owner
mismatch as `unknown` (inconclusive, 0 adjustment) instead of `warning`
(-5.0), while a genuine different-owner mismatch still warns unchanged. See
`fetch_and_build.py` (`detect_package_provenance_drift`) and the regression
tests in `tests/test_helpers.py`.

### Also corrected: the original dominance calculation was wrong

The original §"Key finding: one dimension dominates" was based on eyeballing
the top-swings table, not a computed aggregate. Recomputed properly (mean of
per-dimension **|adjustment|**, not the netted total, which sign-cancellation
distorts): drift was **37%** of the summed mean adjustment before this fix —
the largest single dimension, but never close to the proposed 60% dominance
threshold. Criterion 3 should have read PASS from the start.

### Criteria, before vs. after

| # | Criterion | Before | After | Status |
|---|---|---|---|---|
| 1 | Churn ≤10% moving >10 ranks | 19% | 18% | still **FAIL** |
| 2 | No A-grade drops >10 unreviewed | 6 | **4** | still **FAIL**, improved |
| 3 | No dimension >60% of adjustment | 37% *(mis-graded fail)* | 34% | **PASS** (correction) |
| 4 | Spec published first | not yet | ✅ `/spec/runtime-trust` live | **PASS** |
| 5 | Top-10 turnover ≤2 | 2 | 2 | **PASS** |

LangGraph and ECC — the two clearest false positives — are now correctly
cleared from the A-grade drop list. The remaining four (Strands Agents,
Hermes Agent, OpenClaw, Open WebUI) are **not** detector bugs:

- Strands Agents / Hermes Agent / OpenClaw's PyPI mismatch point to genuinely
  *different* owners — real ambiguity between squatting and an unrelated name
  collision that a URL comparison alone cannot resolve.
- Open WebUI's drop was **never driven by drift** (`unknown` status, 0
  adjustment) — it's `external_dependencies` (-4.0) and `tool_plugin_surface`
  (-1.8). It was mis-attributed in the original top-drops table.

### Verdict: still **NO-GO**, for a narrower reason

Churn (criterion 1) is not primarily a drift problem — it's spread across all
four runtime dimensions, so fixing drift's false positives alone was never
going to clear a 10% churn ceiling. Two real paths forward, owner's call:

1. **Investigate the remaining ambiguous cases manually** (confirm whether
   Strands/Hermes/OpenClaw's mismatched packages ever belonged to the
   project) — resolves criterion 2 but not criterion 1's broader churn.
2. **Revisit whether the 10% churn ceiling is the right bar** for a first-pass
   calibration touching four independent signals at once — a stricter
   per-dimension rollout (e.g., ship MCP + drift as v2 first, hold
   ext-deps/tool-surface for a second pass) might clear the ceiling by
   reducing how many dimensions can move any one agent at once.

## Addendum 3 (2026-07-02): audit of external_dependencies and tool_plugin_surface

Owner directive: "no compromise on quality of scores and leaderboard." The
prior two addenda only audited `package_provenance_drift`. The remaining two
runtime dimensions had never been checked for the same class of problem —
and they had it, worse.

### Two real bugs found

1. **Substring-matching bug (`detect_external_service_dependencies` and
   `detect_tool_plugin_surface` shared this pattern).** Dependency markers
   were matched with naive `marker in manifest_text`, and several markers
   were dangerously short (`"pg"`, `"pty"`, 2-3 chars) — capable of matching
   inside unrelated tokens. **Fixed:** a new `_manifest_has_dep_marker()`
   tokenizes manifest text on real separators and requires the marker to
   *start* a token, so `"pg"` still matches `"pgvector"` but can no longer
   match inside an unrelated word.
2. **README-mention-as-evidence design flaw (bigger issue).** Both functions
   let a bare README/description keyword match count identically to real
   dependency-manifest or credential-marker evidence. This systematically
   over-penalized exactly the most mature, flexible, popular frameworks —
   e.g. Haystack showed 5 "providers," but only 2 (OpenAI, Postgres) had any
   dependency-file evidence; the other 3 (Anthropic, Azure OpenAI, Amazon
   Bedrock) were pure prose mentions of *supported, optional* integrations,
   not hard dependencies. Same pattern in `tool_plugin_surface`: the
   "search"/"code" tag patterns (bare `\bsearch\b`, `\bgithub\b`,
   `\brepository\b`) are common enough to match almost any README regardless
   of genuine capability. **Fixed:** both functions now require real
   manifest-dependency or credential-marker evidence to count toward the
   score; a README mention alone is logged as supplementary evidence but no
   longer inflates `providers`/`tool_tags`.

### Scale of impact (confirms this was a real, systemic problem)

- **122 of 319 agents (38%)** had their provider count change.
- **220 of 319 agents (69%)** had their tool-tag count change.
- Spot-checked Open WebUI (a genuine A-grade drop, not previously explained by
  drift): its `external_dependencies` penalty is legitimate (OpenAI, Anthropic,
  Amazon Bedrock all have real manifest/credential evidence) — left unchanged,
  correctly. Its `tool_plugin_surface` tags dropped from ~5 to 1 (`browser`,
  the only one with real `playwright` dependency evidence) — the other 4 were
  pure README noise, now correctly removed.

### Final re-run — all three fixes combined (drift same-owner + agents.json
corrections + this audit)

| Criterion | Original | Final | Status |
|---|---|---|---|
| 1. Churn ≤10% moving >10 ranks | 19% (61 agents) | **14%** (45 agents) | still **FAIL**, much closer |
| 2. No A-grade drops >10 unreviewed | 6 unreviewed | **1** (Open WebUI — confirmed legitimate, not a bug) | effectively **PASS** |
| 3. No dimension >60% of adjustment | 37% (mis-graded fail) | 43% (drift's *share* rose as the other two dimensions' false-positive mass shrank, but still well under 60%) | **PASS** |
| 4. Spec published first | not yet | ✅ `/spec/runtime-trust` live | **PASS** |
| 5. Top-10 turnover ≤2 | 2 | 2 | **PASS** |

Top-25 turnover also improved: 4 → 3.

### Verdict: still **NO-GO** — but the remaining gap is not a detector-quality problem, it's leaderboard density

Four of five criteria pass; the single blocker is churn (14%, need ≤10%).

**Tested and disproven:** a phased rollout (`mcp` + `package_provenance_drift`
only, holding `external_dependencies`/`tool_plugin_surface` for later) was
the obvious next hypothesis — verified it numerically rather than asserting
it. It does **not** help; churn is actually *worse* (15%) with two dimensions
than with all four cleaned up (14%), because relative rank shifts don't scale
down linearly with fewer active signals.

**The real cause, checked directly:** adjacent ranks on the leaderboard sit a
**median 0.1 trust-score points apart** (mean 0.29). Every agent that moved
>10 ranks did so on a **genuine, evidence-backed** adjustment — median 3.7
points, none smaller than 0.9. On a leaderboard this densely packed, *any*
real multi-point score change will always cross dozens of rank positions;
that is a property of rank-position density, not a symptom of signal noise.
Three consecutive rounds of detector auditing found and fixed real bugs each
time (drift same-owner false positives, 3 wrong package-name guesses,
README-mention inflation touching 38-69% of agents) and churn only moved
19%→18%→14% — diminishing returns, because the remaining churn was never a
bug to find.

**This means criterion 1 itself measured the wrong thing.** A ≤10%-of-agents-
move->10-ranks ceiling conflates leaderboard density with signal
instability — the same 3-point adjustment would look "stable" in a sparse
top-10 and "unstable" in this densely-packed field, regardless of how correct
the underlying evidence is. I am not redefining or loosening this criterion
myself — that would be exactly the kind of compromise ruled out — but flagging
it as a design flaw in the original proposal (mine) for the owner to decide:
either accept the churn as expected given leaderboard density (and measure
stability differently going forward — e.g. score-point drift or percentile-
band movement, not raw rank position), or hold T3.4 entirely pending further
work neither of us has yet defined. The detector-quality work (this
addendum + the two before it) is genuinely complete and does not need
revisiting again on this basis.

## Addendum 4 (2026-07-02): every remaining drift warning investigated — zero real risks found

Rather than stop at the 3 A-grade cases, checked the *entire* remaining
warning list, and found a pattern the same-owner fix couldn't catch: a
**cross-owner repo transfer** (project moved to a new org — GitHub 301s the
old name to the new one). `detect_package_provenance_drift` gained a
`tracked_repo_canonical` parameter, populated from the `full_name` field
GitHub's API already returns on every `get_repo()` call (zero new network
calls) — when a package points to that canonical name instead of our
possibly-stale tracked repo, it's scored `unknown`, not `warning`.

**Confirmed transfers (code fix, applies going forward to any project):**
Garak (`leondz/garak` → `nvidia/garak`), Google Genkit (`firebase/genkit` →
`genkit-ai/genkit`), Ragas (`explodinggradients/ragas` →
`vibrantlabsai/ragas`), Superagent (`homanp/superagent` →
`superagent-ai/superagent`).

**Investigated the final 6 unresolved agents individually** (live registry
queries, same method as the original 3):
- **Verl Agent** — `pypi_package: verl` was the *upstream* Volcano Engine RL
  library it depends on, not its own package (confirmed: no `verl-agent`
  package exists on PyPI at all). Removed.
- **Continue**, **Bolt**, **Goose** — pre-existing, unrelated packages that
  predate or have nothing to do with the tracked project (`continue` on npm:
  2013, unrelated async utility; `bolt` on npm: 2011, JS project-management
  tool; `goose` on crates.io: 2017, an unrelated load-testing framework).
  Same generic-word-collision pattern as the original Strands Agents case.
  Removed.
- **RAGFlow** — `pypi ragflow` is authored by `breezedeus`, not `infiniflow`
  — very likely an unrelated or unofficial package, not RAGFlow's own.
  Removed.
- **OpenHuman** — `crates.io openhuman` (homepage `openhuman.ai`) is a
  genuinely different, real "OpenHuman" project, not the tracked
  `tinyhumansai/openhuman`. A real name collision between two unrelated real
  projects. Removed.
- **OpenManus** — **not fixed, left as-is.** `pypi openmanus`'s author field
  literally reads "mannaandpoem and OpenManus Team" — a genuinely real
  package, just attributed to the original creator's personal repo
  (`mannaandpoem/openmanus`) rather than the `FoundationAgents/OpenManus` org
  we track. This is an editorial question (which repo is canonical after a
  foundation handoff?), not a data-quality bug — deliberately not resolved
  unilaterally.

### Result: of the original ~26 warning-status agents, every single one now
### traces to a false positive. Zero genuine supply-chain risks were found.

None were malicious squatting or hijacking. All were: same-owner variants
(12), wrong package-name guesses in our own config (9: Strands, Hermes,
OpenClaw, Verl Agent, RAGFlow, Continue, Bolt, Goose, OpenHuman), or
