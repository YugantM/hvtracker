Methodology

v1.1 · Last updated 2026-05-23

Philosophy

HVTracker measures what is independently observable. We do not accept submissions, self-reported claims, or maintainer surveys. Every signal comes from public APIs that anyone can query and verify.

The composite health score rewards sustained activity and real-world adoption over vanity metrics. Stars alone are easy to acquire; the combination of stars, active development, package downloads, and community discussion is much harder to fake. The methodology will evolve as new measurable signals become available; each major change increments the version number and is logged in the changelog at the bottom of this page.

Data Sources

GitHub REST API
Stars, forks, commit count over the last four weeks, days since last push, repository description, primary language, and open issue count. Refreshed weekly.
Star counts can be inflated by short-term campaigns. We mitigate by log-scaling and weighting against freshness, activity, and forks.
npm Registry
Weekly download counts for JavaScript/TypeScript agents that publish packages listed in agents.json. Refreshed weekly.
Download figures reflect package installs, not distinct users, and may include CI mirrors.
PyPI (via pypistats)
Weekly download counts for Python agents that publish packages. Refreshed weekly.
PyPI statistics aggregate all install types; they overstate interactive use relative to automated pulls.
Docker Hub
Total image pull counts for agents distributed as containers (where a docker_image is configured). Refreshed weekly.
Docker pull counts are cumulative and never decrease — they favor older images.
Hacker News (Algolia API)
Count of story mentions matching a curated search term over the last 30 days. Refreshed weekly.
Search terms are hand-tuned to reduce false positives; agents with generic names may be omitted.

Scoring Formula

The health score is a composite from 0 to 100, summed from four components with fixed maximums:

Score = stars(30) + freshness(25) + activity(25) + community(20)
  • Stars · 30% — min(30, ln(1 + stars) / ln(1 + 100,000) × 30). Log-scaled against a fixed anchor of 100,000 stars. Rewards adoption without letting megarepos dominate linearly.
  • Freshness · 25% — max(0, 25 × (1 − days_since_last_push / 180)). Linear decay to zero over six months of inactivity. A recent push is a necessary signal of maintenance.
  • Activity · 25% — min(25, ln(1 + commits₄wk) / ln(1 + 100) × 25). Commits summed over the last four weeks (GitHub commit-activity API). Log-scaled; 100 commits in that window earns the full 25 points.
  • Community · 20% — min(20, ln(1 + forks) / ln(1 + 20,000) × 20). Fork count as a proxy for downstream reuse; log-scaled against 20,000 forks.

Package download counts (npm/PyPI), Docker pull totals, and Hacker News mentions are collected and shown on the leaderboard but are not yet incorporated into the score. They will be folded into v1.2 once enough historical data accumulates to set sensible weights.

What We Don't Measure (Yet)

  • Runtime correctness on real coding tasks — planned for v2.0 via independent benchmarking.
  • Real-world usage outcomes — planned for v3.0 via opt-in signed telemetry.
  • Security posture — CVE counts and security advisory tracking under consideration for v1.3.
  • Documentation quality — no automated rubric yet.
  • API stability and breaking-change frequency — not tracked.
  • LLM provider compatibility — not tracked.

Versioning

Methodology changes are versioned explicitly. Every revision is recorded in the changelog below. Raw data snapshots are preserved on each build so past leaderboard states remain auditable — see the historical snapshots in the repository.

Changelog
